
Appendix A: Reproducible Dataset and Model Procedure

A1 Records and Scope
This appendix reconstructs the procedure from the saved generator, training code, model, metrics and export artifacts. The commands are reproducibility instructions; they are not a claim that training was repeated during report revision. The existing forest was preserved. A separate scratch directory should be used when reproducing a result so that the original model and metrics are not overwritten.
The original development workspace contains src/soil_ml, data/synthetic, models, reports and firmware/esp32_soil_edge/include. Python, NumPy and pandas provide the generation and training environment. The supplied source archive preserves the relevant files, the synthetic CSV, the saved forest JSON, the exported header and the metrics. The generated-header listing is the exact model used by the current gateway, with visual line wrapping in the document only.
A2 Dataset Inspection
Step 1. Inspect the proposed public CSV before adapting it. Record its column names, row count, labels and units where actually documented. The saved audit found 2,200 rows and 22 classes, with N, P, K, temperature, humidity, ph, rainfall and label. It found no cabbage class and no direct EC, soil-moisture or reference-sensor columns.
Step 2. Compare those columns with the raw sensor vector SM, ST7in1, pH, N, P, K, EC, STDS18B20 and SMCap. A spelling change from ph to pH is possible, but replacing humidity with soil moisture or rainfall with EC would change the physical meaning. Temperature metadata must establish whether the value is air or soil temperature before it is treated as equivalent.
Step 3. Record the mismatch rather than silently completing the dataset with unexplained values. The synthetic route was chosen for prototype development because the available data could not support the intended complete vector and four labels. No local farm records were added under the guise of synthetic observations.
A3 Synthetic Generation
Step 4. Define the four explicit crop profiles shown in Table A.1. These are simulation assumptions chosen for the prototype. They are not a published crop-requirement table, and the cited literature does not validate their numerical means or standard deviations.
Step 5. Initialize numpy.random.default_rng with seed 42. For each crop and each primary feature, draw 250 values from its normal distribution. Clip moisture to 0–100%, temperature to −10–60°C, pH to 3.5–9.5, N and P to 0–200 mg/kg, K to 0–250 mg/kg and EC to 0–5 mS/cm. These are software generation/validation bounds, not the calibrated limits of the probe.
Step 6. Generate SMCap from SM plus normal noise with standard deviation 2, and generate STDS18B20 from ST7in1 plus normal noise with standard deviation 0.4. Apply the corresponding moisture and temperature clipping. The backup readings are correlated with the simulated primary quantities by construction.
Step 7. Add the profile's crop label, concatenate the four 250-row frames, retain the declared column order and shuffle with random_state=42. Save soil_synthetic_prototype.csv. Check that there are 1,000 rows and 250 examples per label and that all required values are finite. Keep the file labelled synthetic.

A4 Splitting and Training
Step 8. Load the CSV with numeric conversion that raises errors. Reject missing feature columns, missing labels, nonfinite values, duplicated rows or classes with fewer than ten examples. These checks prevent obvious data-processing errors; they do not assess agricultural validity.
Step 9. Use the seeded stratified splitter. It allocates 70% training and 15% validation by class, then assigns the remainder to test. The resulting counts are 700, 150 and 150. Each crop contributes 175 training rows. Validation support is 38, 38, 37 and 37 in alphabetical class order; test support is 37, 37, 38 and 38.
Step 10. Fuse valid paired moisture and temperature readings. Use the mean for an agreeing pair and the single valid value when the other is unavailable. During training the generated complete inputs satisfy the original healthy-input workflow. Keep pH, N, P, K and EC in their stated units and do not introduce a scaling transform that the exported model does not implement.
Step 11. Fit TinyRandomForest using only the fused training rows. Its configuration is 15 estimators, depth five, minimum leaf size two, up to 16 candidate thresholds and random_state=42. For seven features, floor(sqrt(7)) gives two candidate features at each split. Bootstrap row sampling and per-tree random streams are seeded. The class order is banana, cabbage, kidneybeans and maize; ties are resolved by the implementation's first-maximum rule.
Step 12. Save the tree structures, class list, feature order, parameters and flattened arrays in soil_rf_desktop.json. Do not report this JSON file as an ESP32-executable program. The board executes the generated C/C++ arrays and traversal code.
A5 Evaluation and Export
Step 13. Run prediction on the untouched validation and test partitions. Build the confusion matrices with rows as actual classes and columns as predicted classes. Calculate per-class and macro metrics using the equations in Chapter Three. The saved test matrix totals 150 records and 143 correct predictions.
Step 14. Preserve metrics.json before further changes. Its historical fusion note describes the earlier withholding policy. That note is not the final missing-data policy; the later transparent wrapper attempts inference using training medians. The original complete-input metrics remain valid only for that original evaluation setting.
Step 15. Flatten each tree into parallel arrays of feature indices, thresholds, child indices and leaf values, with tree offsets. Export crop_model.h and edge_model_metadata.json. Compare the original and exported traversals with the saved tests. Compilation confirms syntax and linkage; numerical parity on the physical board still requires an execution test.
Step 16. Estimate core constant-array storage using 555 × (1 + 4 + 2 + 2 + 1) + 15 × 2 = 5,580 bytes. Keep this estimate separate from total program flash and runtime memory, which include libraries, buffers, tasks and communications.
A6 Missing and Invalid Inputs
Step 17. Derive seven medians from the fused 700-row training partition, convert them to float32 and save fallback_metadata.json. In model feature order, they are 52.7340850830, 23.1939487457, 6.2782726288, 82.0555419922, 52.3586654663, 55.8350715637 and 1.1199320555. The units follow the feature table.
Step 18. Apply input validation, backup recovery and disagreement handling before substitution. A missing or invalid raw channel is disclosed. If the physical quantity remains unresolved, substitute its saved training median only in the inference vector. Record which features were substituted and how many physical quantities were measured.
Step 19. Label results as complete_inputs, provisional or default_data_only. These labels describe input availability, not calibration or accuracy. In particular, a complete_inputs result can still be wrong because a sensor is biased or because the field differs from the synthetic profiles.
Step 20. Check all 1,000 complete-input rows against the unchanged model, all 512 missing-channel combinations and the 36 saved invalid-value cases. Check backup recovery, disagreements and the all-missing case. These are functional tests of the wrapper. They do not provide a new field-accuracy estimate or authorize retraining.

From the extracted source package's training directory, set PYTHONPATH to src. Use the commands below only in a scratch copy if reproducing training. B2 Integration Steps Completed in Source
I preserved the existing model and included its headers in the gateway. I built the raw nine-channel vector from the seven primary quantities, DS18B20 and installed capacitive channel, converted EC to mS/cm for inference, and kept missing raw values separate from model substitutions.

B3 Pin Assignments and Modem Naming
I used the current configuration listed below: SIM800C TX to ESP32 GPIO17 and SIM800C RX to GPIO16; capacitive AOUT to GPIO35 with 3.3 V supply; common-cathode RGB R25/G33/B23 with cathode at GND; active buzzer GPIO26. I did not infer hidden solder continuity from the enclosure photograph.
The modem input is reported as 4.7 V at its carrier. Identify whether the carrier regulates that input before comparing it with the bare SIM800C's 3.4–4.4 V specification. Do not treat a software configuration value as evidence of a measured voltage. A record should include the carrier identification, voltage at its supply connector, voltage at the modem supply and behavior during transmission.

B5 Controlled Hardware Test Sequence
First check power rails and signal-level compatibility with the pump load disconnected. Confirm relay OFF at boot, display initialization, 1-Wire acquisition and Modbus response decoding. Compare readings with an appropriate reference before setting the sensor-map verification flag. Checking a CRC alone is insufficient.
Next test pump hysteresis with a controlled input source and an isolated or supervised load: below 35%, exactly 35%, between the thresholds, exactly 60% and above 60%. Confirm the three-cycle start condition, stale-data shutdown, disconnection shutdown and 60-second fault latch. Record the actual output and timestamp rather than only whether a function was called.
Then configure a recipient in private SMS_PHONE and enable SMS after modem power and registration are verified. Confirm an initial crop/status message, a provisional message with missing inputs, a pump ON event, a pump OFF event and a pump FAULT event. Photograph or otherwise record the received messages with personal numbers removed from public evidence. A modem submission counter alone is not a delivery record.
Finally run the complete telemetry path and verify new device timestamps, receiver rows, cloud acceptance and dashboard updates. Disconnect Wi-Fi and stop the computer processes to verify that local functions remain independent and that the dashboard marks saved data accurately. Record any gaps; QoS 0 and the newest-only bridge do not replay every lost sample.
B6 Compiler Workaround and Outstanding Tests
The Windows self-extracting build helper encountered a temporary-directory permission error. The previous successful workaround used esptool 5.1.0 Python source and the selected Espressif board package's partition/insights scripts. It retained the Espressif C/C++ compiler and libraries. This resolved compilation; it did not resolve or test a physical modem, probe or pump.
Outstanding tests include actual ESP32 prediction parity against known vectors, inference timing, peak heap use, sensor calibration, supply stability, enclosure durability and successful receipt of SMS. The source's default false flags document that commissioning boundary. Enabling features in a separate compiler fixture is useful to check code paths, but such a fixture is not an operational configuration for the device.

C4 Receiver and Bridge Operation
The receiver subscribes using its scoped broker credentials, validates messages and writes accepted events to SQLite. The bridge reads the newest suitable record without modifying the database and sends it over HTTPS using its own ingestion key. The combined launcher starts both processes, and the computer must remain awake for remote updates to continue.
The source archive includes receiver.py, cloud_bridge.py, run_monitor.py and the launchers. Their private configuration locations reflect the installed project layout and must be adjusted when moving the project to a different computer. No populated bridge configuration or database containing operational data is included. Keep private configuration outside the dashboard publication directory.
Stopping the receiver stops new local receipt. Stopping the bridge stops cloud uploads but does not remove already stored local events. Stopping the computer does not stop code executing on a separately powered ESP32, but it does stop this chosen remote data path. A cloud receiver would move those two processes to another machine and require server upkeep and funding; it would not train or calibrate the ESP32 model automatically.
C5 Maintenance Procedure
Check that the receiver and bridge are running, that device timestamps advance and that storage has free space. Back up the SQLite database using a consistent SQLite backup procedure, rather than copying an actively changing database without considering its journal. Review failed uploads and SMS counters, and keep keys out of public source and screenshots.
When updating firmware, preserve a known working source version and repeat the commissioning tests affected by the change. When updating the dashboard, run its checks, record the deployment and verify production access. A future model change requires a new dataset/version record, training/evaluation evidence, export and firmware upload. GitHub version control can support that process; it is not an implemented continual-learning system in this project.
Appendix D Test Definitions and Interpretation

D1 Classification Results
The saved metrics describe one deterministic synthetic-data experiment. Macro metrics weight the four crop classes equally. The confusion matrices use alphabetical class order. A higher test accuracy than validation accuracy is possible with different small held-out samples; it is not evidence that the test set was larger or more representative.
The synthetic test confusion matrix contains seven errors: one cabbage-to-banana, three cabbage-to-maize and three maize-to-cabbage. Accuracy is 143/150 × 100 = 95.33%. Banana precision is 37/38, whereas its recall is 37/37. Cabbage precision is 33/36 and recall is 33/37. Kidney beans has 38/38 for both. Maize has 35/38 for both. These denominators explain why the per-class metrics differ.
D2 Functional Tests
The receiver tests cover validation and lifecycle behavior using controlled inputs, including malformed payloads, wrong devices, nonfinite values and duplicate handling. They are not field-delivery experiments. The cloud tests exercise access controls, payload filtering, history retention and replay behavior in controlled stores. They do not establish unlimited production retention or perfect connectivity.
The wrapper tests preserve the trained forest and exercise incomplete input handling. The 512 missingness combinations correspond to 2^9 availability patterns for the raw channels. A prediction in each case establishes software coverage, not equal reliability across those patterns. All-default estimates must remain visibly distinct from estimates based on measurements.
D3 Hardware Evidence Register
I recorded the informal visit as limited author-confirmed context, synthetic metrics as saved computational results, and uploaded serial output as hardware communication evidence. I recorded user-confirmed SMS reception and TFT readability separately from modem submission counts. I recorded the shared-supply blackout as unresolved and laboratory calibration as not completed.
D4 Acceptance Records for Future Testing
For each physical test, record date and time, firmware identifier, board and peripheral identification, configuration flags, input condition, expected response, observed response and supporting log or photograph. For a crop prediction, record the raw values, units, validity decisions, substituted features and class output. For SMS, record both modem acknowledgement and the recipient's receipt time. For irrigation, record relay state and actual water delivery separately.

0006 def valid(value, low, high):
0007     return math.isfinite(value) and low <= value <= high
0008 
0009 def pair(a, b, low, high, tolerance):
0010     av, bv = valid(a, low, high), valid(b, low, high)
0011     if av and bv:
0012         return ((a + b) / 2, "fused") if abs(a - b) <= tolerance else (float("nan"), "disagreement")
0013     if av or bv:
0014         return (a if av else b), "backup"
0015     return float("nan"), "missing"

0017 def fuse(row):
0018     moisture, ms = pair(row["SM"], row["SMCap"], 0, 100, 15)
0019     temperature, ts = pair(row["ST7in1"], row["STDS18B20"], -10, 60, 5)
0020     features = [moisture, temperature]
0021     for name, high, low in [("pH", 9.5, 3.5), ("N", 200, 0), ("P", 200, 0), ("K", 250, 0), ("EC", 5, 0)]:
0022         value = row[name]
0023         features.append(value if valid(value, low, high) else float("nan"))
0024     available = sum(math.isfinite(v) for v in features)
0025     status = "normal" if available == 7 and ms == ts == "fused" else "degraded" if available == 7 else 
     "monitor_only"

0027             "recommendation_enabled": available == 7, "moisture": ms, "temperature": ts}

0203     def _best_split(self, x, y, indices, feature_count, rng):
0204         n_features = x.shape[1]
0205         size = min(feature_count, n_features)
0206         feature_indices = rng.choice(n_features, size=size, replace=False)
0207         base_impurity = self._gini(y[indices])
0208         best_gain = 0.0
0209         best = None
0210         for feature in feature_indices:
0211             values = x[indices, feature]

0213             if len(unique) <= 1:
0214                 continue

0223                     len(left_indices) * self._gini(y[left_indices])

0228                     best_gain = gain

0232     def _candidate_thresholds(self, unique: np.ndarray) -> np.ndarray:
0233         if len(unique) <= self.max_thresholds:

0236         sampled = unique[np.unique(np.rint(positions).astype(int))]
0237         if len(sampled) <= 1:
0238             return sampled
0239         return (sampled[:-1] + sampled[1:]) / 2.0

0021 inline int predict_soil_crop(const float x[SOIL_FEATURE_COUNT]) {
0022   uint8_t votes[SOIL_CLASS_COUNT] = {0};
0023   for (uint8_t t = 0; t < SOIL_TREE_COUNT; ++t) {
0024     uint16_t base = pgm_read_word(&TREE_OFFSETS[t]);
0025     int node = (int)base;
0026     while (true) {
0027       int8_t feature = (int8_t)pgm_read_byte(&TREE_FEATURE[node]);
0028       if (feature < 0) {
0029         int8_t klass = (int8_t)pgm_read_byte(&TREE_VALUE[node]);
0030         votes[klass]++;
0031         break;
0032       }
0033       float threshold = pgm_read_float(&TREE_THRESHOLD[node]);
0034       int16_t child = x[feature] <= threshold
0035         ? (int16_t)pgm_read_word(&TREE_LEFT[node])
0036         : (int16_t)pgm_read_word(&TREE_RIGHT[node]);
0037       node = (int)child + (int)base;
0038     }
0039   }
0040   uint8_t best = 0;
0041   for (uint8_t i = 1; i < SOIL_CLASS_COUNT; ++i) {
0042     if (votes[i] > votes[best]) best = i;
0043   }
0044   return best;

0003 inline bool sensorValid(float v, float low, float high) {
0004   return isfinite(v) && v >= low && v <= high;
0005 }
0006 inline float fusePair(float a, float b, float low, float high, float tolerance, bool& 
     degraded) {
0007   bool av = sensorValid(a, low, high), bv = sensorValid(b, low, high);
0008   if (av && bv) return fabsf(a-b) <= tolerance ? (a+b)/2 : NAN;
0009   degraded = true;
0010   return av ? a : bv ? b : NAN;
0011 }
0012 struct FusionResult { float features[7]; int available; bool degraded; };
0013 // Raw: SM, ST7in1, pH, N, P, K, EC, STDS18B20, SMCap.
0014 // Acquisition must mark stale, failed or quarantined channels NAN.
0015 inline FusionResult fuseSensors(const float raw[9]) {
0016   FusionResult r = {{0}, 0, false};
0017   r.features[0] = fusePair(raw[0], raw[8], 0, 100, 15, r.degraded);
0018   r.features[1] = fusePair(raw[1], raw[7], -10, 60, 5, r.degraded);
0019   const float lows[5] = {3.5,0,0,0,0}, highs[5] = {9.5,200,200,250,5};
0020   for (int i=0; i<5; ++i)
0021     r.features[i+2] = sensorValid(raw[i+2], lows[i], highs[i]) ? raw[i+2] : NAN;
0022   for (int i=0; i<7; ++i) if (isfinite(r.features[i])) ++r.available;

G1 How I Acquired the Seven Soil Parameters
I connected the digital probe through the RS485 interface and used GPIO27 to select bus direction. The ESP32 UART uses RX19 and TX4 at 9600 baud with 8 data bits, no parity and one stop bit. In readRegister(), I constructed a Modbus request for slave 1, function 03 and one register, added CRC16, enabled transmission, sent and flushed the bytes, and returned the interface to receive mode. I allowed a bounded reply interval and rejected a reply with an invalid length, address, function, byte count or CRC.

In readSoil(), I requested all seven registers and accepted the new primary set only if the complete cycle passed. I checked moisture from 0 to 100%, temperature from -55 to 125 degrees Celsius and pH from 0 to 14. I stored lastGood and the accepted values together. If the cycle failed, I marked the primary probe unavailable and requested pump OFF. The 8,000 ms stale limit protects control from old primary readings; it is not the dashboard freshness threshold.
For example, a raw moisture response of 253 displays as 25.3%, and pH 700 displays as 7.00. These are arithmetic examples, not additional observed measurements. I did not hard-code the TFT to display pH 7.00; it came through the selected register conversion. Repeated pH near 7 and EC/NPK zeros require reference investigation. CRC-valid communication alone does not verify the probe’s internal chemical sensing method, nutrient selectivity, register interpretation or measurement accuracy. I kept SENSOR_MAP_VERIFIED false because I did not complete that validation.
 
G2 How I Added and Calibrated the Capacitive Reference
I used the capacitive blade as an analog reference channel. Its sensing circuit responds to changes around the blade and produces an analog output; I read that output on GPIO35 rather than requesting a Modbus register. I powered the sensor from 3.3 V, used a common ground, and configured a 12-bit ADC with the recorded attenuation setting. The exact sensor response is empirical: I did not establish a universal conversion from voltage to soil water content.
I initially kept the percentage unavailable because a live voltage alone did not establish dry and wet endpoints. I requested a dry-air condition and a wet-blade condition, keeping the upper electronics dry. Early readings were nearly identical and did not support calibration; I requested another controlled condition instead of manufacturing endpoints. I subsequently recorded dry 2260 mV and wet 993 mV using CAP_DRY and CAP_WET and stored them in Preferences under soil-cap. I checked them with CAP_STATUS.
I calculated relative moisture as 100 times (dry voltage minus measured voltage), divided by (dry voltage minus wet voltage), and limited the result to 0–100%. I required the dry endpoint to exceed the wet endpoint by more than 100 mV. For a 1050 mV reading, the stored endpoints give approximately 95.5%. As a result, the TFT and telemetry can display a relative percentage. This is two-point normalization using air and water, not a gravimetric or volumetric soil calibration. Later drift remains a repeatability concern.
 
G3 How I Prepared Trained and Exported the Model
I first audited the proposed public dataset and found that it lacked cabbage and did not contain interchangeable soil-moisture or EC fields. I recorded that mismatch. I then defined four synthetic profiles, drew 250 examples per class with seed 42, clipped the values to explicit bounds and generated the two reference channels with added noise. Appendix A retains every generation, split, evaluation and export step, its profile table, commands and source listings E1–E11. I did not repeat training during this report update.
I fused the two moisture readings and the two temperature readings into seven model quantities, using the recorded agreement thresholds of 15 percentage points and 5 degrees Celsius. I used a stratified 700/150/150 split. I fitted 15 bootstrap trees with maximum depth five and minimum leaf size two, selected splits by impurity reduction and combined outputs by voting. I retained the resulting 555-node forest and evaluated its held-out synthetic predictions. I exported thresholds, children and class values into crop_model.h, so the ESP32 follows compiled comparisons instead of running Python or contacting a cloud model.
At runtime I supplied the raw channels to transparent_inference.h, checked missing/invalid values, handled reference disagreement and used training-derived medians only for unresolved model features. I reported missing, invalid, filled and disagreeing channels separately. I kept raw absent measurements absent in telemetry. The model predicts one of banana, cabbage, kidneybeans and maize; it does not predict NPK, water demand, yield or a fertilizer dose. No online retraining or automatic GitHub-to-device learning is active.

G5 How I Implemented Pump Control and Found the Power Fault
I implemented irrigation as explicit threshold logic rather than as the crop classifier’s output. In the current demonstration logic, starting requires enabled operation, fresh primary data, valid capacitive calibration, three good primary cycles, a 120-second boot delay, both moisture values below 35% for 30 seconds and a 60-second restart interval. Once running, either moisture value at 60% or above requests OFF. Invalid readings, stale primary data and a latched fault also block pumping. An independent timer limits continuous operation to 60 seconds.
I enqueued telemetry and SMS on pump transitions so that they did not wait for the normal publication interval. I confirmed a brief ON/OFF action during commissioning. Later, the pump cycled and the TFT/RGB darkened; I confirmed the pump shared its supply with the controller/display. I set ENABLE_AUTO_PUMP false and left the demonstration disarmed. I did not enable it merely because a wet reference sensor was expected to inhibit it. A software OFF report does not measure actual water flow, and a power reset can interrupt reporting.
 
G6 How I Configured and Verified SMS
I configured the SIM800C recipient privately and corrected the UART orientation after the original connection did not produce the required result. The working code uses ESP32 RX17 receiving modem TX and ESP32 TX16 driving modem RX. I used AT, text mode CMGF=1, CSMP settings requesting reports, CNMI configuration and CMGS. I sent the body after the modem prompt and ended it with Ctrl-Z. I counted +CMGS followed by OK as submission; I treated a matching successful +CDS report as network-confirmed delivery.
I revised cropSMSBody() to include all nine readings in TFT order, then pump state, provisional crop and missing/invalid/substituted diagnostics. I used ASCII text and split longer bodies into numbered SMS messages. N, P and K use mg/kg, EC uses uS/cm, temperature uses C and moisture uses %. I observed submission failures/timeouts and later received confirmation that messages had arrived. After reconnection on COM4, the log showed network registration and eight submissions with one failure since boot. I did not assume those counters proved delivery of every part.
The current implementation freezes each body when queueSMS() receives it. A queue or delivery-report wait can delay later parts, so I have not achieved the requested exact sending-time freshness. I recorded this limitation explicitly rather than changing the firmware during the report task. A future correction should refresh a coherent sample immediately before starting a summary and attach its sample timestamp to all parts.
